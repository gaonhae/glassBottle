#  PRD: 가족 소통 개선 웹서비스 (MVP)

---

## 0. 문서 정보

| 항목     | 내용                        |
| ------ | ------------------------- |
| 문서명    | 가족 소통 개선 웹서비스 PRD         |
| 문서 목적  | MVP 범위의 제품 요구사항과 구현 기준 정의 |
| 문서 버전  | v1.0                      |
| 제품 단계  | MVP                       |

### 0.1 문서 작성 원칙

* 이 문서는 **아이디어 설명용**이 아니라 **MVP 구현 기준서**를 목표로 한다.
* 구현자가 임의 해석하지 않도록 가능한 한 기능, 상태, 권한, 완료 기준을 명시한다.
* 명확히 결정되지 않은 사항은 별도 **오픈 이슈**로 분리한다.

## 1. 제품 개요

### 1.1 제품명 (가칭)

* 유리병 (GlassBottle)

### 1.2 제품 정의

가족 간의 정서적 연결을 강화하기 위해, 질문 기반 대화와 지연 전달 편지 경험을 제공하는 **모바일 웹 기반 비동기 가족 소통 서비스**.

### 1.3 한 줄 정의

> 가족 대화를 “의지”가 아니라 “시스템”으로 만든다.

---

## 2. 배경 및 문제 정의

### 2.1 핵심 문제

* 부모와 자녀가 물리적으로 떨어져 살수록 대화 빈도와 깊이가 감소할 수 있다.
* 가족 간 대화는 종종 안부 확인 수준에서 멈추고, 가치관·감정·기억을 공유하는 대화로 이어지지 않는다.
* 연락은 중요하지만, 바쁨·어색함·타이밍 문제로 인해 실제 행동으로 이어지지 않는다.

### 2.2 문제 구조

| 문제          | 원인                      | 결과            |
| ----------- | ----------------------- | ------------- |
| 대화 빈도 감소    | 바쁨, 생활 리듬 차이, 심리적 거리    | 관계 약화         |
| 깊이 있는 대화 부족 | 공통 화제 부족, 감정 표현의 어색함    | 정서적 연결 저하     |
| 연락의 부담      | 지금 연락해도 될지 모름, 즉시 응답 부담 | 미루기, 습관 형성 실패 |

### 2.3 해결 접근

* 공통 질문을 통해 **대화 시작 비용**을 낮춘다.
* 답변을 카드형으로 모아 보여줌으로써 **가족의 생각을 쉽게 소비**할 수 있게 한다.
* 유리병 편지를 통해 **즉시 반응 압박 없이 감정 전달**이 가능하도록 한다.

---

## 3. 타겟 사용자

### 3.1 Primary Target

* 부모와 떨어져 거주하는 20대 청년

### 3.2 Secondary Target

* 40~50대 부모

### 3.3 타겟 특성

| 사용자군   | 특성                        | 제품 설계 시 의미             |
| ------ | ------------------------- | ---------------------- |
| 20대 자녀 | 바쁨, 메시지 습관은 있으나 깊은 대화는 적음 | 빠른 참여, 부담 없는 UX 필요     |
| 부모     | 디지털 친숙도가 다양함              | 단순한 UI, 큰 버튼, 짧은 문구 필요 |

### 3.4 핵심 가정

* 가정: 사용자는 가족과 더 깊게 연결되고 싶지만, 이를 실행할 계기와 구조가 부족하다.
* 가정: 부모 세대도 **매우 단순한 모바일 웹 UX**라면 사용할 수 있다.
* 추측: 댓글은 긴 토론보다 짧은 반응성 대화에 가까울 때 심리적 부담이 덜하다.

---

## 4. 제품 목표

### 4.1 제품 목표

* 가족 간 **정기적 상호작용**을 유도한다.
* 가족 간 **깊이 있는 대화 발생률**을 높인다.
* 서비스 사용에 대한 **심리적·행동적 부담**을 최소화한다.

### 4.2 성공 지표 (KPI)

| 지표         | 목표                 |
| ---------- | ------------------ |
| WAU        | 가족 그룹 기준 70% 이상    |
| 질문 응답률     | 60% 이상             |
| 답변 카드 열람률  | 70% 이상             |
| 댓글 작성률     | 질문 응답 세션 대비 20% 이상 |
| 유리병 편지 열람률 | 80% 이상             |
| 4주 유지율     | 40% 이상             |

### 4.3 비목표 (Non-goals)

다음 항목은 MVP 범위에 포함하지 않는다.

* 실시간 채팅
* 음성/영상 메시지
* 좋아요/이모지 반응
* 댓글 대댓글
* 첨부파일 업로드
* AI 감정 분석
* 데스크톱/태블릿 최적화 UI

---

## 5. 핵심 가치 제안

### 5.1 사용자 가치

* 별도의 대화 주제를 고민하지 않아도 가족과 깊은 대화를 시작할 수 있다.
* 가족의 답변을 한 화면에서 쉽게 볼 수 있다.
* 답장을 바로 해야 한다는 부담 없이 감정을 전달할 수 있다.

### 5.2 제품 포지셔닝

* 메시지 앱의 대체재가 아니라, **가족 대화의 촉매제** 역할을 하는 서비스
* 빈번한 커뮤니케이션보다, **작지만 의미 있는 상호작용**을 목표로 하는 서비스

---

## 6. 사용자 시나리오 / User Stories

### 6.1 청년 사용자

* 독립 거주 중인 사용자는 가족과 대화를 시작할 계기가 없을 때, 오늘의 질문을 보고 부담 없이 자신의 생각을 남기고 싶다.
* 사용자는 가족 구성원들의 답변을 한 번에 확인하고, 공감되거나 궁금한 부분에 짧게 댓글을 남기고 싶다.
* 사용자는 상대가 언제 읽을지 몰라 더 솔직해질 수 있는 방식으로 편지를 보내고 싶다.

### 6.2 부모 사용자

* 부모 사용자는 복잡한 메뉴 탐색 없이 가족의 답변을 한 화면에서 쉽게 보고 싶다.
* 부모 사용자는 특정 답변을 눌러 간단한 댓글을 남기고 대화를 이어가고 싶다.
* 부모 사용자는 작은 글씨와 복잡한 조작 없이 서비스의 핵심 기능만 직관적으로 사용하고 싶다.

---

## 7. 사용자 경험 원칙

### 7.1 핵심 UX 원칙

* **간단해야 한다**: 주요 기능은 홈 화면 기준 1탭 또는 2탭 이내에서 접근 가능해야 한다.
* **부담이 적어야 한다**: 응답 강제, 미응답 압박, 과도한 알림을 지양한다.
* **감정 표현을 돕되 과장하지 않는다**: 따뜻한 톤은 유지하되, 감성적 연출이 사용성을 해치면 안 된다.
* **부모 친화적이어야 한다**: 큰 터치 영역, 큰 텍스트, 낮은 정보 밀도를 유지한다.

### 7.2 부모 친화성 기준

| 항목       | 기준              |
| -------- | --------------- |
| 주요 버튼 크기 | 최소 44px 높이 이상   |
| 주요 CTA 수 | 한 화면당 1~2개 중심   |
| 문구 길이    | 짧고 일상적인 한국어 사용  |
| 조작 단계    | 핵심 작업 2단계 이내 지향 |
| 입력 부담    | 긴 폼 입력 지양       |

### 7.3 감정적 부담 최소화 정책

* 질문 답변은 강제하지 않는다.
* 댓글 작성은 선택이다.
* 미응답 사용자에게 죄책감을 유도하는 UI를 두지 않는다.
* 알림은 리마인드 역할까지만 수행하며 압박 수단으로 사용하지 않는다.

---

## 8. 플랫폼 정책

### 8.1 지원 범위

* MVP는 **모바일 웹 전용**으로 제공한다.
* 지원 디바이스는 스마트폰 브라우저 기준이다.
* PC 및 태블릿은 비지원 디바이스로 간주한다.

### 8.2 비지원 디바이스 처리

* PC/태블릿 접속 시 서비스 기능 화면을 노출하지 않는다.
* 대신 “모바일로 접속해 달라”는 안내 화면만 표시한다.
* MVP 단계에서는 비모바일 사용자의 이탈을 의도적으로 감수한다.

### 8.3 기술적 감지 기준

* User-Agent와 viewport 정보를 조합하여 모바일 여부를 판별한다.
* 판별 정책은 서버 또는 클라이언트 중 한 곳에 일관되게 정의한다.

## 10. 핵심 기능 요구사항

## 10.1 질문 기반 소통 (Conversation Prompts)

### 기능 설명

* 가족 그룹 전체에 동일한 질문을 제공한다.
* 각 구성원은 질문에 대해 텍스트 답변을 작성한다.
* 작성된 답변은 한 페이지에서 카드 형태로 모아 조회한다.
* 각 카드를 클릭하면 답변 상세 화면으로 이동하며, 해당 답변에 댓글을 작성할 수 있다.

### 세부 요구사항

| 항목    | 요구사항                       |
| ----- | -------------------------- |
| 질문 발행 | 시스템이 질문을 발행한다              |
| 발행 빈도 | 기본 하루 1회                   |
| 답변 형식 | 텍스트                        |
| 답변 노출 | 질문별 카드 리스트                 |
| 카드 정보 | 작성자 이름, 작성 시각, 답변 일부 또는 전체 |
| 카드 클릭 | 답변 상세 화면 이동                |
| 댓글    | 가족 구성원 누구나 작성 가능           |
| 공개 범위 | 동일 가족 그룹 내                 |

### Acceptance Criteria

* 사용자는 특정 질문에 대한 가족 전체 답변을 한 페이지에서 카드 리스트 형태로 조회할 수 있어야 한다.
* 각 카드는 작성자, 작성 시간, 답변 본문 일부 또는 전체를 표시해야 한다.
* 카드 전체 영역은 터치 가능해야 한다.
* 카드 터치 시 답변 상세 화면으로 이동해야 한다.
* 답변 상세 화면에는 질문 본문, 선택한 답변 전체 내용, 댓글 목록, 댓글 입력창이 보여야 한다.
* 댓글은 작성 후 즉시 목록에 반영되어야 한다.

---

## 10.2 유리병 편지 (Delayed Message)

### 기능 설명

* 사용자가 가족 구성원에게 편지를 작성하면, 시스템이 랜덤한 미래 시점에 편지를 전달한다.
* 발신자와 수신자 모두 정확한 도착 시점을 알 수 없다.

### 세부 요구사항

| 항목    | 요구사항                                  |
| ----- | ------------------------------------- |
| 전송 대상 | 같은 가족 그룹 내 구성원                        |
| 편지 형식 | 텍스트                                   |
| 전달 시간 | 랜덤 (예: 1시간 ~ 72시간)                    |
| 상태    | drafted / floating / delivered / read |
| 도착 알림 | 수신자에게 전달 시 알림                         |
| 공개 범위 | 발신자와 수신자만 열람 가능                       |

### Acceptance Criteria

* 사용자는 편지를 작성하고 전송할 수 있어야 한다.
* 편지 전송 후 시스템은 랜덤한 도착 시간을 설정해야 한다.
* 도착 전에는 수신자가 편지를 열람할 수 없어야 한다.
* 도착 후 수신자는 편지를 읽을 수 있어야 한다.
* 발신자는 편지가 “떠다니는 중”인지 “도착했는지” 상태를 확인할 수 있어야 한다.

---

## 10.3 가족 그룹 관리

### 기능 설명

* 사용자는 가족 그룹을 생성하거나 초대 링크를 통해 기존 가족 그룹에 참여할 수 있다.

### 세부 요구사항

| 항목    | 요구사항      |
| ----- | --------- |
| 그룹 생성 | 최초 사용자 가능 |
| 그룹 참여 | 초대 링크 기반  |
| 최대 인원 | 오픈 이슈     |
| 링크 만료 | 오픈 이슈     |

### Acceptance Criteria

* 사용자는 가족 그룹을 생성할 수 있어야 한다.
* 사용자는 유효한 초대 링크를 통해 가족 그룹에 참여할 수 있어야 한다.
* 유효하지 않거나 만료된 초대 링크에 접근하면 에러 안내가 표시되어야 한다.

---

## 10.4 모바일 전용 접근 정책

### Acceptance Criteria

* 스마트폰이 아닌 디바이스로 접속한 경우, 주요 기능 화면은 렌더링되지 않아야 한다.
* 비지원 디바이스에는 모바일 접속 안내 화면만 표시되어야 한다.
* 모바일 디바이스에서는 정상적으로 서비스 기능이 노출되어야 한다.

---

## 11. 권한 / 접근 제어 정책

### 11.1 기본 원칙

* 미로그인 사용자는 서비스 핵심 데이터에 접근할 수 없다.
* 질문, 답변, 댓글은 같은 가족 그룹 내 사용자만 열람할 수 있다.
* 유리병 편지는 발신자와 수신자만 열람할 수 있다.

### 11.2 권한 매트릭스

| 대상           | 질문 조회 | 답변 조회 | 댓글 조회 | 댓글 작성 | 편지 조회 | 편지 작성 |
| ------------ | ----- | ----- | ----- | ----- | ----- | ----- |
| 같은 가족 그룹 구성원 | 가능    | 가능    | 가능    | 가능    | 일부 가능 | 가능    |
| 다른 가족 그룹 사용자 | 불가    | 불가    | 불가    | 불가    | 불가    | 불가    |
| 미로그인 사용자     | 불가    | 불가    | 불가    | 불가    | 불가    | 불가    |

### 11.3 세부 규칙

* 유리병 편지 조회는 **발신자와 수신자만 가능**하다.
* 같은 가족 그룹 구성원이라도 자신이 당사자가 아닌 편지는 볼 수 없다.
* 답변과 댓글은 가족 그룹 내부에서만 조회 가능하다.

## 13. 사용자 흐름

### 13.1 온보딩 플로우

1. 사용자가 서비스에 접속한다.
2. 로그인 또는 가입한다.
3. 가족 그룹을 생성하거나 초대 링크를 통해 참여한다.
4. 홈 화면으로 이동한다.

### 13.2 질문 상호작용 플로우

1. 사용자가 홈에서 오늘의 질문을 확인한다.
2. 자신의 답변을 작성한다.
3. 질문 상세 화면에서 가족 구성원의 답변 카드를 한 번에 확인한다.
4. 특정 카드를 클릭한다.
5. 답변 상세 화면에서 댓글을 조회하거나 작성한다.

### 13.3 유리병 편지 플로우

1. 사용자가 유리병 편지 작성 화면으로 이동한다.
2. 수신자를 선택하고 편지를 작성한다.
3. 편지를 전송한다.
4. 시스템이 랜덤 도착 시점을 설정하고 상태를 floating으로 변경한다.
5. 도착 시점이 되면 상태를 delivered로 변경한다.
6. 수신자가 편지를 읽으면 상태를 read로 변경한다.

| 네트워크 오류       | 재시도 CTA 제공               |
| 권한 없는 접근      | 접근 불가 안내 또는 홈으로 리다이렉트    |
| 비지원 디바이스 접속   | 모바일 접속 안내 화면 표시          |

## 16. 콘텐츠 정책

### 16.1 기본 원칙

* 서비스는 가족 간 정서적 소통을 돕는 목적을 가진다.
* 불쾌감, 혐오, 노골적 폭력 등 명백히 부적절한 콘텐츠는 운영 정책 대상이 될 수 있다.

### 16.2 MVP 기준 정책

* 답변/댓글/편지의 신고 기능은 MVP 범위에서 제외한다.
* 답변/댓글 수정·삭제 가능 여부는 오픈 이슈로 둔다.
* 명백한 악성 사용 사례는 운영자 수동 대응 전제로 시작한다.

## 17. 개인정보 / 보안 정책

### 17.1 기본 원칙

* 가족 간 대화 데이터는 사적 성격이 강하므로 외부 노출을 최소화해야 한다.
* 최소 권한 원칙으로 접근을 제한해야 한다.

### 17.2 보안 요구사항

* 인증되지 않은 사용자는 질문, 답변, 댓글, 편지 데이터에 접근할 수 없어야 한다.
* 가족 그룹 간 데이터가 섞이거나 노출되면 안 된다.
* 편지는 당사자 외 열람이 불가능해야 한다.
* 초대 링크는 예측 불가능한 토큰을 사용해야 한다.

### 17.3 개인정보 처리 관점의 고려사항

* 탈퇴 시 사용자 데이터 처리 정책 필요
* 가족 그룹 탈퇴 시 기존 작성 콘텐츠 보존 정책 필요
* 편지/답변/댓글 보존 기간 정책 필요

## 20. 비기능 요구사항 (NFR)

### 20.1 성능

* 모바일 브라우저 기준 주요 화면은 체감상 빠르게 열려야 한다.
* 첫 화면 로딩 지연이 사용 이탈로 이어질 수 있으므로 과도한 리소스 로딩을 피한다.

### 20.2 사용성

* 모바일 세로 화면 기준으로 설계한다.
* 한 손 조작을 고려한다.
* 큰 글씨, 넓은 여백, 단순한 시각 구조를 유지한다.

### 20.3 안정성

* 편지 전달 스케줄링은 누락되면 안 된다.
* 동일 편지가 중복 전달되지 않도록 설계해야 한다.

### 20.4 접근 제어

* familyGroup 단위의 멀티테넌시 격리를 준수해야 한다.
